## Мета та прийняті рішення

Приватний каталог для одного користувача FBReader на чинному Hetzner-сервері
поряд із наявним ботом. Переїзд бота й OPDS разом на новий сервер — окремий
проєкт, який не входить у поточну реалізацію.
Перша версія: останні завершені книги, пошук на Searchfloor, пагінація,
завантаження повного файлу на вимогу. Без повного локального індексу,
архіву файлів, підписки, Telegram-інтерфейсу та конвертації EPUB.
Кеш відновлюється на вимогу без бекапу. Регулярні релізи — через автодеплой
після merge у main та успішного CI; налаштування хоста потрібне один раз.
Успіх: у FBReader можна додати URL, знайти завершену книгу, завантажити
й відкрити її; бот продовжує працювати незалежно від OPDS.

## Джерела та встановлені факти

  token-managed Cloudflare Tunnel, Litestream → R2, монітор диска/inode.
- [Поточний package.json](https://github.com/ysilvestrov/warsaw-beer-bot/blob/main/package.json)
  і [deploy/README.md](https://github.com/ysilvestrov/warsaw-beer-bot/blob/main/deploy/README.md)
  вказують Node ≥24 / Node 24; spec ще містить ≥20. Фактичну версію хоста перевіряє CLI.
- Публічний HTML `https://searchfloor.org/?status=is_finished`: кнопка
  `.download-btn` містить ID і `data-url="/book/{id}"`; анонімний формат `fb2.zip`.
- Публічний `/static/js/root-1.5.9.js`: звичайний Download переходить на
  `data-url`; пошук `/search?q=...`; наступна сторінка додає `page`.
- HEAD `/book/25415` повернув 200 та `application/zip`, але довжину 0.
  Це підтверджує маршрут, а не валідність GET-файлу. GET і ZIP/FB2 перевірити в прототипі.
- Поєднання пошуку зі `status=is_finished` ще не перевірено. Парсер мусить
  перевіряти завершеність кожної картки незалежно від query-фільтра.
- Аудит підтвердив доступність Searchfloor із чинного Hetzner-хоста
  на час перевірки; це не гарантія майбутньої доступності.

## Повторне використання

### Уточнення після серверного аудиту

Джерело: `docs/server-audit.md`, завершено 2026-10-04 о 22:14 Europe/Warsaw.
На чинному хості підтверджено Node 24.19.0, 4 CPU, 7.6 GiB RAM;
у короткому вимірі доступно близько 6 GiB RAM, 34 GiB диска і 2.09 млн inode.
Порт `127.0.0.1:8787` вільний у snapshot, не зарезервований. Code-server
історично сягав 5.91 GiB RAM: ці виміри не доводять запас під час dev-піків.
Searchfloor із цього хоста повертає справжні списки завершених книг і пошук;
наступна сторінка може бути HTML-фрагментом. Семантика status-фільтра пошуку
та GET Download залишаються неперевіреними. Аудит production не змінював.

Початкові пропозиції аудиту, не встановлені ліміти: runtime MemoryHigh=256 MiB,
MemoryMax=384 MiB, CPUQuota=50% одного CPU, TasksMax=64, одна Download-передача;
кеш до 256 MiB, поточний і попередній settled release. Перевірити на прототипі.
Cloudflare mapping, права bootstrap і доступ нового deploy-user до
`ysilvestrov/opds-proxy` та exact-SHA CI ще не підтверджені.

### Узгодження з планом розділення dev / production

Контекст: чат «Оптимізувати Linux-хостинг HostPro»,
`codex://threads/01a0dede-6f18-77a0-845b-d3c6b7edee3d`.
У ньому заплановано чистий production VPS 2 vCPU / 4 ГБ / 40 ГБ;
чинний хост лишається для Codex, тестів і збірок. Це план, не підтвердження
виконаного переїзду. Останнє уточнення власника: зараз розгортаємо OPDS поряд
із ботом на чинному сервері. Спільний переїзд — окремий проєкт; тут не купуємо
VPS, не переносимо бота й не змінюємо його release process. Для майбутнього
проєкту зберегти виміри OPDS runtime, кешу й двох релізів. Старий аудит не
переноситься автоматично на новий хост.

Автодеплой має підтримувати доставку готового артефакту з dev/CI, без npm ci
та build на production. Для native better-sqlite3 артефакт мусить відповідати
OS/архітектурі/Node ABI цільового хоста; Windows-збірку не переносити на Linux.
На production — перевірка SHA/CI/цілісності, розпакування в staging,
активація, health і rollback. Доступ до приватних артефактів перевіряється
окремо від доступу до git. Збірка на чинному dev-хості має власні ліміти
і cleanup; її розміщення в CI також можливе.

| Ресурс | Як використати | Межа |
|---|---|---|
| Hetzner та ОС | Розмістити ще один невеликий сервіс | Запас RAM/CPU/диска встановити аудитом |
| Node/TypeScript | Той самий перевірений runtime і strict TS | Не оновлювати системний Node заради OPDS |
| Cloudflare Tunnel та DNS-зона | Новий hostname → вільний loopback-порт | Окремий маршрут; hostname ще не створено |
| systemd | Окремий unit, Unix-користувач, каталоги, restart і resource limits | Не додавати OPDS у процес бота |
| SQLite/WAL | Окрема база метаданих/кешу | Не використовувати bot.db |
| Litestream/R2 | Для OPDS не потрібні | SQLite містить лише відновлюваний кеш |
| Монітор root FS | Уже контролює спільний диск/inode | Не вважається монітором здоров'я OPDS |
| Hono, cheerio, p-queue, zod, pino, Vitest | Ті самі бібліотеки та перевірені патерни | Не копіювати пивну бізнес-логіку |
| Merge-deploy / rollback | Адаптувати pull-autodeploy після merge та зеленого CI | Окремі шляхи, lock/state/unit; одноразове встановлення |

Варіанти: додати endpoint у бот — менше конфігурації, але спільні збої й релізи;
окремий сервіс на цьому хості — рекомендовано; окремий VPS — додаткова вартість
без доведеної потреби. Для MVP Docker і Redis не потрібні.

## Запропонована архітектура

`FBReader → HTTPS/Cloudflare Tunnel → окремий Hono OPDS service → Searchfloor`.
SQLite містить метадані та кеш запитів. Шлях завантаження передає ZIP потоком
без постійного запису на диск.

Модулі:
- `sources/searchfloor`: HTTP, список, пошук, пагінація, перевірка карток,
  отримання Download. HTML-парсери відокремлені від мережі.
- `domain`: модель Book, завершеність, доступність файлу, стабільні ID.
- `storage`: SQLite, міграції, кеш за нормалізованими query/page/filter.
- `opds`: Atom XML 1.2, навігація, acquisition, OpenSearch, XML escaping.
- `api`: авторизація, маршрути, обмеження запитів, помилки, health.
- `index`: конфігурація, залежності, запуск, graceful shutdown.

Маршрути: `/opds` (список джерел), `/opds/searchfloor` (корінь джерела),
`/opds/searchfloor/completed?page=…`, `/opds/searchfloor/search?q=…&page=…`,
`/opds/searchfloor/opensearch.xml`, `/opds/searchfloor/books/{id}/download.fb2.zip`, `/health`.
`searchfloor` — public name, адаптер працює з searchfloor.org. У v1 інших джерел
немає. Зарезервовані `/opds/{name}/authors[/{authorId}]` та
`/opds/{name}/genres[/{genreId}]`, з optional source-local refs у моделі книги.
Їх реалізація відкладена: v1 повертає 404 й не показує неробочих links.
Деталі серій/авторів — метадані; окремі каталоги серій/авторів можна додати пізніше.
Усі посилання OPDS мають вести через приватний сервіс, із коректним зовнішнім base URL.

Приватний доступ: кандидат — HTTP Basic поверх HTTPS, якщо конкретний FBReader
передає credentials і для каталогу, і для acquisition. Це перевіряється до
вибору остаточного механізму. Browser-login Cloudflare Access не припускати
сумісним із читалкою. Не використовувати beer-api токени. Випадковий URL-токен
можливий лише як окремо погоджений fallback із редагуванням логів і ротацією.

Download: приймати лише відомий ID завершеної книги, будувати upstream URL
із дозволеного origin; довільні URL від клієнта не приймати. Перевіряти
redirect destinations; не пропускати HTML challenge/login як ZIP. Коректні
Content-Type і Content-Disposition, обмеження розміру, таймаут, скасування
upstream при відключенні клієнта, максимум 1–2 паралельних завантаження.
Не вимагати конкретний ZIP MIME без перевірки: джерело може віддавати octet-stream.
Формат OPDS acquisition для ZIP/FB2 узгодити практичним тестом FBReader.

Кеш: початково 15 хв для списків/пошуку, до доби для метаданих книги;
обмеження кількості записів і регулярне видалення прострочених. Об'єднання
однакових запитів, окрема черга до Searchfloor, backoff на 429/503.
Застарілий кеш при недоступному джерелі допускається з обмеженим віком;
помилка джерела не має перетворюватися на «книг немає».
Пагінація зберігає query і завершеність; якщо потрібна локальна фільтрація,
bounded дочитування сторінок із cursor, щоб не пропускати книги й не зависати.

SQLite — витратний кеш: за відсутності БД створюється порожня, дані
підтягуються лише для запитаних сторінок. Без масового прогріву. При несумісній
версії схеми кешу створюється новий кеш; старий файл видаляється після закриття
з'єднань і в межах обмеженої політики зберігання. Перші запити після втрати кешу
будуть повільнішими; якщо джерело недоступне, відновлення доведеться відкласти.
Конфігурація та пароль не зберігаються в кеші. Несекретна конфігурація є в
репозиторії, секрети відновлюються окремо з наявного сховища власника.

## Автодеплой

Рекомендований варіант — окремий pull-deployer за зразком бота: systemd timer
на сервері перевіряє main кожні 5 хвилин. Не потрібен вхідний SSH із GitHub Actions.
Право merge у main означає дозвіл на звичайний production-реліз.
Джерело релізів — `ysilvestrov/opds-proxy`; `main` є запропонованою deployment
branch, її наявність і налаштування CI потрібно підтвердити перед встановленням.

1. Вибрати незмінний commit SHA, перевірити успішний CI саме для нього,
   блокувати паралельні деплої окремим lock; не повторювати невдалий SHA без
   явного retry або нового коміту.
2. Отримати готовий Linux-артефакт для exact SHA, створений у dev/CI;
   перевірити походження, checksum та відповідність runtime. Розпакувати
   в окремому staging, не зачіпаючи активний реліз. Зберегти попередній
   працездатний реліз; на production не встановлювати залежності й не збирати код.
3. Перемкнути current на готовий реліз, перезапустити тільки OPDS unit,
   перевірити локальний health/readiness і автентифікований XML каталогу.
   Здоров'я процесу не залежить від доступності Searchfloor; зовнішній збій
   джерела не повинен спричиняти rollback коду.
4. Якщо старт або перевірка неуспішні — повернути попередній реліз і restart.
   Rollback БД не потрібен: попередній код повинен уміти відкинути несумісний
   кеш і створити його заново. Health не вимагає прогрітого кешу.
5. Зберегти SHA, стан і журнал останнього deployment. Обмежити кількість
   release-каталогів; передбачити pause/retry/manual rollback.

Одноразово встановлюються unit, timer, каталоги, deploy-user, вузькі права
restart, доступ читання репозиторію/статусу CI/артефактів та tunnel-route. Сервісний
користувач не має права змінювати деплоєр або sudoers. Зміни системних unit,
секретів, прав, runtime чи tunnel-route потребують окремого operator-кроку:
звичайний автодеплой доставляє тільки код та безпечну конфігурацію.
Цей механізм не використовує lock/state/sudoers бота.

## Послідовність реалізації

1. Read-only аудит чинного хоста виконано: `docs/server-audit.md`.
   Закрити лише його конкретні прогалини. Повторний аудит нового VPS
   належить окремому проєкту переїзду.
2. Контрактний прототип: HTML списку/пошуку/наступної сторінки; один GET Download
   у тимчасовий файл; перевірка ZIP із FB2 та відкриття в конкретному FBReader.
   Підтвердити Basic auth і MIME/filename. Якщо хост отримує challenge, переглянути
   транспорт; браузер/relay не входить у цей MVP автоматично.
3. Реалізувати adapter і фільтр повних книг на збережених HTML fixtures:
   позитивні, незавершені, недоступні, порожні й змінені сторінки.
4. Додати OPDS 1.2 та OpenSearch, стабільні entry ID, start/self/next,
   абсолютні URL; перевірити XML, українські/кириличні назви та спецсимволи.
5. Додати SQLite-кеш, чергу, таймаути/backoff і streaming download.
   Перевірити 403/429/5xx, HTML замість книги, редиректи, великий файл,
   повторний запит, переривання клієнта й неправильну авторизацію.
6. Окремий systemd deployment, наприклад `/opt/search-floor-opds`,
   `/etc/search-floor-opds`, `/var/lib/search-floor-opds`; порт обрати після аудиту.
   Resource limits встановити за вимірами. Додати новий tunnel hostname.
7. Налаштувати окремий pull-autodeploy з CI gate і rollback. Перевірити
   успішний реліз, невдалий старт, несумісний кеш, pause/retry, обмеження
   кількості релізів і незалежність бота. Операторський доступ — лише для
   першого встановлення й подальших інфраструктурних змін.
8. Acceptance: FBReader → root → пошук → next → Download → читання;
   після рестарту кеш працює; журнал не містить паролів; bot health і
   його restart counter не змінилися. Після втрати кешу запити відновлюють
   потрібні дані. Merge із зеленим CI виконує реліз без ручного SSH.

Документ є погодженим базовим дизайном для детального implementation plan
за Superpowers. Bootstrap виконується після підготовки та огляду конкретних
серверних файлів; поточне погодження не означає вже виконаний deployment.
